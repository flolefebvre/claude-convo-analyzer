# CI

`.github/workflows/ci.yml` runs on every pull request, whatever its base branch, and every push to `main`, and the release workflow calls it (`workflow_call`, see "Release" below). A superseded run on the same ref is cancelled, except on `main`, where every push keeps its run. Its jobs run in parallel: `static`, `test`, `test-windows`, `build`, `e2e` and `package`; `smoke` waits for `package`, and `ci` for all seven.

- Give each stage of the `gate` line in package.json its own job, and each script in it its own step, in the gate's order, so a failing check names itself in the run summary. The `test` script is the one exception, run by two jobs: `test` on `ubuntu-latest` and `test-windows` on `windows-latest`, since the app runs on native Windows too. `test-windows` runs the whole suite unsharded; a test that fails only there is fixed at its cause, never skipped on Windows. Developing on Windows (the repo scripts, `pnpm gate`, seeding) is not supported, so no other gate stage runs there; only `smoke`, which tests the package users install, also runs on Windows and macOS.
- Keep the summary job named `ci`: it is the one status check a branch ruleset requires, so a renamed job blocks every merge. Add every new job to its `needs`, and keep its `if: ${{ !cancelled() }}` and its check that every needed job succeeded — a required check that is skipped counts as passing, so without them a failed job would leave a mergeable PR.
- Split the test suite by adding a number to the `test` job's `shard` list when that job becomes the longest one; the shard count is read from the list.
- Restore caches only for tools that reuse them across runs, and place them after the install. The incremental caches — `node_modules/.cache` (Prettier, ESLint) and `tsconfig.tsbuildinfo` in `static`, `.next/cache` in `build` — are keyed on the lockfile and the commit, and restored from the latest key with the same lockfile. The Playwright browsers in `e2e` (`~/.cache/ms-playwright`) are keyed on the runner OS and the installed `@playwright/test` version (`hashFiles` on its `package.json`), not the lockfile, so an unrelated dependency bump keeps the download; they have no restore-keys, since a browser built for another Playwright version is never used.
- The `build` job runs `pnpm build`, which fails when `next build` prints Turbopack's warning block, even though `next build` itself exits 0 after it. The job log then ends with `Build failed: next build printed a Turbopack warning, and pnpm build allows none:` and the block again; the warning also shows where `next build` printed it, after the static pages are generated. Fix the warning at its call, never by hiding it with `turbopack.ignoreIssue`. The `e2e` job's own build runs `next build` directly and is not guarded.
- The `e2e` job restores the Playwright browsers and, on a miss, installs Chromium (`pnpm exec playwright install chromium`); it relies on the Chromium libraries the `ubuntu-latest` image already ships; if Chromium fails to launch after an image update, restore `--with-deps`. It then runs `pnpm e2e`. That builds its own test build (`EXPOSE_TESTING_API=1`) and serves it seeded; it never reuses the `build` job's output. If the job fails, it uploads `playwright-report/` as an artifact for 7 days, the only way to debug a failure that happens only on CI.
- The `package` job runs `pnpm package`, which builds the npm package from its own standalone `next build` (`NPM_PACKAGE_BUILD=1`, guarded like `pnpm build`) and packs it, then uploads the tarball as the `package-tarball` artifact for 7 days. The `smoke` job, the one job that waits on another, runs on `ubuntu-latest`, `windows-latest` and `macos-latest` (`fail-fast: false`, so one OS's failure does not hide another's). Each downloads that tarball and runs `pnpm smoke --tarball` on it, in bash on every OS so the `*.tgz` glob expands: npm installs it into a temp directory outside the checkout, and the smoke drives the installed launcher on the runner's Node (the script's header lists its checks). Pack once and smoke that tarball on every runner, never repack per runner: it is the file the release publishes. A smoke that fails on one OS is fixed at its cause in `scripts/smoke.ts` or `scripts/package.ts`, never by dropping the OS from the matrix. A smoke that fails after a Next or pnpm upgrade usually means `scripts/package.ts`'s assumptions about the standalone layout broke; it fails the package itself, naming the assumption, when it can tell.
- Put a step every job needs in `.github/actions/setup`, the composite action each job calls right after checkout, never copied into the jobs.
- Pin `node-version` to the major the repo is developed on, never a range that lets CI drift onto a major nobody has run.
- Keep `pnpm/action-setup` ahead of `actions/setup-node`, which needs pnpm on the PATH for `cache: pnpm`. It takes no `version` input: pnpm resolves from the `packageManager` pin in package.json.

Before pushing a change to a workflow, lint them all with `docker run --rm -v "$PWD:/repo" -w /repo rhysd/actionlint:latest`.

## Release

`.github/workflows/release.yml` runs on every pushed `v*` tag, and nothing else. Its jobs run in sequence, each only if the one before succeeded:

1. `version`, before anything is built, classifies the tag against package.json's `version` (`scripts/classify-release-tag.ts`, its rule in `scripts/release-tag.ts`) and exposes the result as the output `kind`. `v<version>` is a `release`, and its tagged commit must also be on `origin/main`: a release is never cut from a branch. `v<version>-<pre-release>` (`v0.1.0-rc.1`) is a `rehearsal`, and may point at any commit. Any other tag fails the job, naming the tag and the version.
2. `ci` calls `ci.yml` itself (its `workflow_call` trigger), so a release passes exactly the checks a pull request does, the three-OS `smoke` included. Never copy a ci job into release.yml: add it to ci.yml, and both run it. A tag push does not trigger ci.yml on its own, so the checks run once.
3. `publish` downloads the `package-tarball` artifact that `ci` packed and smoked, the same run's, and publishes that file, never a rebuild: `npm publish <tarball> --provenance --access public`, then `gh release create <tag> <tarball> --verify-tag --generate-notes`, whose notes are the titles of the pull requests merged since the previous tag, with the tarball attached. On a `rehearsal`, `npm publish` gets `--dry-run` and no GitHub release is created; everything else runs as for a `release`.

`publish` holds the only write permissions (`id-token: write`, `contents: write`); the workflow's default is `contents: read`. It authenticates to npm by trusted publishing (OIDC) only, and no npm token is stored anywhere. The trusted publisher, in the package's settings on npmjs.com, is a GitHub Actions one with repository `flolefebvre/claude-convo-analyzer`, workflow `release.yml` and no environment, so keep the file's name and publish from no other workflow. Under its **Allowed actions**, enable direct `npm publish`: the form allows only `npm stage publish` by default, and the step runs `npm publish`. Never set `NODE_AUTH_TOKEN` on the step: while it is set, even empty, npm publishes with it and never attempts OIDC. Trusted publishing needs npm 11.5.1 or later; the job prints the npm that Node 24 bundles and upgrades it when it is older. `publish` builds nothing, so it neither checks out the repo nor calls the setup action: `actions/setup-node` with `registry-url` (the `.npmrc` the OIDC exchange needs) and no cache is all it installs.

To cut a release:

1. In a pull request, bump `version` in package.json (`npm version <major|minor|patch> --no-git-tag-version`), and merge it.
2. Optionally rehearse: tag the merge commit `v<version>-rc.1`, push the tag, watch the run go green, then delete the tag (`git push origin --delete <tag>`, `git tag -d <tag>`).
3. Tag the merge commit `v<version>` (`git tag v<version> <merge commit>`), and push the tag (`git push origin v<version>`).

A release that fails before `publish` published nothing: fix the cause in a pull request, then delete the tag and tag the new merge commit. A version npm has published can never be published again, so a failure after `npm publish` (in `gh release create`) is finished by hand with that command, not by re-tagging.
